## 1. 目的と背景

同人誌即売会などのイベントで、頒布物(本・グッズ)の持ち込み数、売上、釣り銭、受託分を、サークル主と売り子のスマホで記録できるようにする。イベント終了後は自動で集計し、**次回の刷り部数と持ち込み数の目安**を根拠つきで示す。さらに、頒布物やイベントごとに**何部売れば元が取れるか(損益分岐点)**をグラフで示す。

まずは自分のサークル用に作り、将来はほかのサークルにも配布する。

### 現状の課題(想定)
| 課題 | 結果 |
|---|---|
| 正の字やメモ帳での手集計 | 終了後の集計が面倒で、記録が残らない |
| 完売したときに本当の需要がわからない | 次も同じ部数を刷り、また早く売り切れる |
| 既刊の売れ行きの落ち方がわからない | 刷りすぎて在庫が積み上がる |
| 現金と売上が合わない | 原因(打ち漏れ・釣り銭ミス・受託分の混入)を切り分けられない |
| 受託分が自分の売上と混ざる | 精算のときに揉めたり、手間がかかったりする |
| 印刷費や出展費を回収できたかわからない | 赤字か黒字かの感覚だけで、価格や部数を決めている |

### 成功指標
- 頒布中の記録が **1件あたり2タップ以内・1秒以内**で終わる
- 終了処理(残数確認と現金の数え合わせ)が **10分以内**で終わる
- 刷り部数の提案に「なぜその数か」が表示され、ユーザーが自分で調整できる

## 2. 対象ユーザーと利用シーン

| ペルソナ | 説明 |
|---|---|
| サークル主(主ユーザー) | 頒布物を登録し、イベントの準備から集計、刷り部数の判断までを行う |
| 売り子(補助ユーザー) | 当日スペースに立ち、**自分のスマホで**サークル主と同じデータに販売を記録する。設定はいじらない |

### 利用シーン
1. **イベント前(自宅)**: 頒布物と価格、セットを登録する。持ち込み数と釣り銭を準備する
2. **頒布中(会場)**: サークル主と売り子が、それぞれのスマホで片手で売上を記録する。どちらの記録も同じイベントのデータにまとまる。**電波が悪い前提**(大型会場ではつながりにくい)
3. **撤収時(会場)**: 残数を数え、現金を数え合わせる。受託分を精算する
4. **イベント後(自宅)**: 集計を確認し、次回の刷り部数と持ち込み数を決める

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| サークル | データの持ち主となる単位。MVPでは1つだけだが、データはすべてサークルに属する形で持つ(§8) |
| 頒布物 | 本・グッズなど販売対象のアイテム。版(初版/再版)ごとに刷り記録を持つ |
| 新刊 / 既刊 | そのイベントが初頒布なら新刊、それ以外は既刊 |
| 持ち込み数 | イベントに持って行った数(自己搬入と直接搬入の合計) |
| 直接搬入 | 印刷所から会場へ直接届く分 |
| 無償出庫 | 見本誌の提出、献本、汚損・破損など、売上にならない出庫 |
| 残数 | 持ち込み数 − 販売数 − 無償出庫数。撤収時に実際の数と照合する |
| 完売時刻 | その頒布物の残数が0になった時刻 |
| 釣り銭準備金 | 開始時に用意した釣り銭(金種別) |
| 受託(委託を受ける) | 他サークルの頒布物を自分のスペースで販売すること。売上は預かり金になる。記録と集計は自分の頒布物とまとめて行い、持ち主で後から分ける |
| 持ち主 | 頒布物の所有者。既定は「自分」。受託分は預けてくれたサークル。集計を分けるときの単位になる |
| 端末 | アプリを使うスマホ1台ごとの単位。同じイベントに複数の端末が参加できる |
| 委託(委託に出す) | 自分の頒布物を他サークルのスペースや書店に預けて販売してもらうこと。**v1.1で対応** |
| イベント種別 | 大規模総合 / 中規模 / オンリーなど。需要の補正に使う |
| 固定費 | 売れた部数に関係なくかかる費用。頒布物なら印刷費・制作費、イベントなら出展費・交通費・宿泊費 |
| 変動費 | 1部売れるごとにかかる費用(委託手数料など)。**MVPでは0**(現金のみ・委託に出さない・通販は対象外のため) |
| 損益分岐点 | 売上と総費用が等しくなる販売部数・売上額。これを超えると黒字 |

## 4. スコープ

### 対象範囲(MVP)
- 頒布物・価格・セットの管理
- 在庫管理(自宅などの保管場所 ↔ イベント)
- イベント中の販売記録(オフライン対応、サークル主と売り子の複数端末)
- 釣り銭と現金の管理
- 受託分の記録と、持ち主別の精算
- イベント後の自動集計
- 次回の刷り部数の目安
- 損益分岐点のグラフ(頒布物別・イベント別)

### v1.1 以降
- 委託に出す(他スペース・書店)の記録と精算(§5.6)
- 次回の持ち込み数の目安、刷り部数のシミュレーションなど(§12)

### 対象外
- **現金以外の支払い**(QR決済・カード)。将来対応する場合に備え、取引に支払い方法の項目を追加できる設計にしておく
- **通販**(BOOTH 等)の販売。在庫にも需要予測にも含めない。通販で在庫が減った分は、棚卸し(F-204)で実際の数に合わせる
- 制作にかけた自分の作業時間を費用として扱うこと
- 会計ソフトとの連携、確定申告書類の作成
- 購入者の個人情報の扱い(**一切保持しない**)

### 5.4 頒布中(レジ画面)
支払いは現金のみとする。

| ID | 要件 | 優先 |
|---|---|---|
| F-401 | 頒布物を大きなボタンで並べ、**タップした品目をカートに入れ、「決済」を押して販売を記録する**(誤って記録しないため。設定で端末ごとに「タップした瞬間に1部を記録する」に切り替えられる)。ボタンは2列で並べ、画面に収まらない分は縦にスクロールして見る。上部の売上表示と下部の取り消し・カートのボタンはスクロールしても固定する。並び順はサークル主が設定できる | M |
| F-402 | 複数の品目をまとめて1件の取引として記録できる(カートモード)。合計金額を大きく表示する。預かり金額をボタン(1000円 / 5000円 / 10000円 / ちょうど)で入れるとお釣りを表示する。預かり金額の入力は任意 | M |
| F-404 | 直前の取引を1タップで取り消せる(取り消しも履歴として残す) | M |
| F-405 | 各ボタンに残数を表示する。残りわずかで色を変え、0になったら「完売」と表示して完売時刻を自動で記録する。完売のボタンはタップしても記録しない(誤タップ防止) | M |
| F-406 | 長押しメニューで、見本誌・献本・汚損を販売とは別に記録できる | M |
| F-406a | **残数0でも販売を記録できる**: 完売のボタンを長押しすると、メニューに「販売を記録(残数0)」が出る。記録すると残数はマイナスで赤く表示し、完売時刻はその品目の最後の販売時刻に更新する。終了処理の残数確認(F-501)では、マイナスの品目を持ち込み数の入力漏れの候補として示し、持ち込み数を直せるようにする | M |
| F-407 | 受託分も自分の頒布物と同じボタンで記録する(当日に分ける操作はいらない)。自分の分と受託分を1件の取引でまとめて買われても、そのまま記録できる。ボタンには持ち主を小さく表示する | M |
| F-408 | 現在の売上合計、販売数、現金の理論残高をいつでも確認できる。値は**すべての端末の記録の合計**(同期済みの分)で、最後に同期した時刻を併記する | M |
| F-409 | 値引きや手入力の金額を記録できる(理由メモつき) | S |
| F-410 | 誤タップを防ぐため、ボタンの間隔を広く取り、ロック(画面固定)モードを用意する | S |
| F-411 | 休憩・離席の時間帯を記録でき、集計のときに販売時間から除外する | C |

※ F-403(支払い方法の切り替え)は、現金のみに決めたため削除した。

### 5.5 終了処理(撤収)
| ID | 要件 | 優先 |
|---|---|---|
| F-500 | 終了処理を始める前に、参加した端末ごとの最終同期時刻と未送信の件数を表示する。未同期の端末があれば警告し、同期またはファイルでの取り込み(F-1006)を促す | M |
| F-501 | 頒布物ごとに理論上の残数を表示し、実際の数を入力すると差異を表示する | M |
| F-502 | 現金を金種別に入力すると、理論残高(釣り銭準備金 + 売上の全体。受託分も含む)との差異を表示する。現金箱は1つにまとめて数える前提 | M |
| F-503 | 差異の原因の候補を示す(打ち漏れの可能性がある品目、受託分の混入、釣り銭の渡し間違いなど) | S |
| F-504 | 受託分の精算書を、まとめた記録から持ち主ごとに分けて自動で作る(販売数、売上、受託手数料、支払額、返却数)。画面共有やスクリーンショットで渡せる形にする | M |
| F-505 | 残数を「保管場所に戻す」「持ち主に返却」に振り分け、在庫に反映する | M |
| F-506 | 終了処理を確定すると、そのイベントの記録をロックする(修正は履歴つきの訂正として行う) | S |

## 6. 刷り部数を算出する方法

ブラックボックスの機械学習は使わず、**説明できる計算**にする。各ステップの値は画面で確認できるようにする(F-804)。

対象は持ち主が「自分」の頒布物だけとする。ただし、受託分の売れ行きも時間帯別の販売曲線(§6.1 の F(t))の材料には使う。需要の材料はイベントでの販売だけで、通販の販売は使わない。

### 6.1 イベントごとの推定需要 D
- **完売しなかった場合**: D = 販売数 S(需要はすべて満たされたとみなす)
- **完売した場合**: 販売数は需要の下限にすぎないため、完売時刻から補正する。

  D = S ÷ F(t)

  - t: 開始から完売までの経過時間の割合(休憩時間を除く)
  - F(t): 同じ種別のイベントで、時刻 t までに売れる量が全体に占める割合(累積販売曲線)
    - 同じ種別で**完売しなかった頒布物**の時間帯別の販売から作る
    - 実績が足りないときは既定の曲線を使う(序盤に偏る形。例: 開始1時間で40%、2時間で65%、3時間で80%)
  - 過大な推定を防ぐため、上限を D ≤ 2.0 × S とする(係数は設定で変更可)

### 6.2 イベント種別の補正
- 予定イベントと同じ種別の実績を優先して使う
- 種別が違う場合は、種別ごとの総販売数の比を規模係数として掛ける(例: オンリーの実績を大規模イベントに換算する)

### 6.3 既刊の減衰
- 同じ頒布物を続けて出したイベントの需要比 Dₙ / Dₙ₋₁ を過去の全頒布物から集め、中央値を減衰率 r とする
- 実績がない間は既定値 r = 0.5 を使う(設定で変更可)
- 予定イベントの k 回目の予測需要: D̂ₖ = 直近の需要(種別補正済み)× rᵏ

### 6.4 新刊の基準値
- 直近3冊の新刊について、初めて出したイベントでの推定需要(種別補正済み)を加重平均する(新しいものほど重くする。重み 3:2:1)
- ユーザーが期待度の係数を設定できる(続編 1.1 / 通常 1.0 / 新ジャンル 0.7 など)

### 6.5 推奨刷り部数
```
必要数 = Σ(予定イベントの予測需要)+ 見本誌・献本の予定数 + イベント以外で確保したい部数(手入力。通販用など)
推奨刷り部数 = 必要数 × (1 + 安全率)− 現在庫 − 入荷予定
            → 印刷所の部数の刻みに切り上げる(F-106)
```
- **3案**: 減衰率と完売補正の係数について、過去実績の25%点・中央値・75%点を使い、控えめ / 標準 / 強気を出す
- 予定イベントの数(何回先までを見るか)は、既定を次の3回とし、ユーザーが変えられる
- 推奨刷り部数が0以下なら「再版不要(在庫で足りる見込み)」と表示する

### 6.6 損益分岐点
同人誌は印刷費をまとめて先に払うため、**印刷費は固定費**として扱う(1部あたりの原価として扱うと、刷った分が売れ残ったときの損が見えなくなる)。

MVPでは現金のみ・委託に出さない・通販は対象外のため、**変動費は0**とする。v1.1で委託に出す機能を入れたときに、委託手数料を変動費として加える。

#### 頒布物別(F-1101)
```
固定費 F = 印刷費(対象の版)+ 制作費(初版のみ。作業時間は含めない)
損益分岐部数 = F ÷ 頒布価格 p(小数は切り上げ)
```
- 損益分岐部数が刷り部数より多い場合は「全部売っても回収できない」と警告する
- セットで売れた分は、セット価格を構成品の通常価格の比で按分して各頒布物の売上とする
- 無償出庫(見本誌・献本)は売上0、費用はすでに固定費に含まれているものとして扱う
- イベント限定価格(F-105)で売った分があるときは、売上の線を実際の平均単価で描く

#### イベント別(F-1103)
```
固定費 F_e = 出展費 + 交通費 + 宿泊費 + 搬入の送料 + 消耗品 +(按分した備品費)
粗利率 g   = (自分の分の売上 − 頒布分の原価)÷ 自分の分の売上
             ※ 頒布分の原価 = 販売部数 × 1部あたり原価(F-103)
受託手数料 c = Σ(受託分の売上 × その持ち主の受託手数料率)
損益分岐売上(自分の分)= (F_e − c)÷ g
```
- グラフの横軸は「自分の分の売上」とする。全体の売上(受託分を含む)は参考として別の目盛りで併記する
- イベント開催前は、前回の同種イベントの粗利率と予定経費から試算する
- 頒布分の原価を含めるかどうかを切り替えられる(含めない場合は「イベントの経費をまかなえたか」だけを見る)

#### 刷り部数のシミュレーション(F-1105)
```
刷り部数 q に対する予想利益 π(q) = p × min(q, 予測需要) − 印刷費(q) − 制作費
```
- 印刷費(q) は価格表(F-108)から求める。予測需要は §6.5 の3案それぞれで計算し、3本の線を描く
- 標準案で利益が最大になる q と、3案のどれかで赤字になる q の範囲を表示する

## 8. データモデル(概要)

```
サークル Circle ──< (以下すべてのデータ)

持ち主 Owner(自分 / 受託元。受託手数料率)──< 頒布物

頒布物 Item ──< 刷り記録 PrintRun(部数・印刷費)
   ├──< 制作費 ProductionCost
   ├──< 印刷所の価格表 PrintPriceTier(部数・総額)
   │
   ├──< セット構成 SetComponent >── 頒布物(セット)
   │
   └──< 在庫移動 StockMovement >── 保管場所 Location(自宅 / 実家 / イベント /〔v1.1〕委託先)

イベント Event ──< 持ち込み EventItem(頒布物・持ち込み数・価格・完売時刻・実残数)
      ├──< 取引 Sale ──< 取引明細 SaleLine(頒布物・数量・単価)
      │        └ 時刻、預かり金額(任意)、取り消し対象の取引ID、記録した端末
      ├──< 無償出庫 Giveaway(見本誌・献本・汚損)
      ├──< 参加端末 EventDevice(端末ID・役割〔主/売り子〕・最終同期時刻)
      ├── 釣り銭準備金 CashFloat(金種別)
      ├── 現金の数え合わせ CashCount(金種別)
      └──< 経費 Expense(種別・予定額・実額)

〔v1.1〕委託先 Consignee(委託手数料率)──< 委託報告 ConsignmentReport
```

設計方針:
- **販売と在庫の変動は追記だけ**のイベントログとして持つ。取り消しや訂正も新しいレコードとして追加し、上書きしない。集計値はログから計算する
- すべてのレコードはUUIDを主キーにする。オフラインの複数端末で記録しても、同期のときに衝突しない(F-1003)
- 同期は「相手が持っていないレコードを送る」だけで成り立つ。販売の記録は追記だけなので、2台が同時に記録してもマージで矛盾しない。取り消しは対象の取引IDを指す新しいレコードとして送る
- マスタ(頒布物・価格など)の編集はサークル主だけが行う(F-1004)ため、衝突はほぼ起きない。起きた場合は後から更新した方を採用し、変更履歴を残す
- 受託分は別テーブルにせず、頒布物の持ち主として持つ。持ち主ごとの集計・精算はその都度計算するので、付け替え(F-709)をしても過去の集計がすべて正しく直る
- 販売の記録には、記録した端末のIDと、端末上の時刻を持たせる(時間帯別の集計と完売時刻に使う)
- 損益分岐の値は保存せず、上記のデータからその都度計算する(費用を後から直しても、グラフが常に最新になる)
- **将来の配布に備え、すべてのデータにサークルIDを持たせる**。MVPの画面はサークル1つ分だけだが、データとアクセス制御はサークル単位で分けておく。あとから複数のサークルが同じサービスを使っても、データ構造を変えずに済む
- 支払い方法は今は持たない。キャッシュレスに対応するときは、取引に支払い方法の列を追加する(既存のデータは「現金」とみなす)
- 金額は整数(円)で扱う

## 9. 非機能要件

| 区分 | 要件 |
|---|---|
| オフライン | レジ画面と終了処理は**通信なしで丸1日動く**。通信が戻ったら自動で同期する |
| 同期 | 通信できる間は、ある端末の記録が5秒以内に他の端末に反映される。同期の失敗や再送で記録が重複・欠落しない |
| 応答性能 | レジのタップから記録・表示の反映まで100ms以内 |
| データ保全 | 1タップごとに端末の記憶領域へ即座に保存する。アプリが落ちても、ブラウザを閉じても記録を失わない |
| 操作性 | 片手・縦持ちで操作でき、ボタンは最小 56×56pt。屋内照明でも見やすいコントラスト |
| 対応端末 | iOS Safari / Android Chrome の最新2バージョン。PC ブラウザでは集計と管理を快適に使える |
| 電池 | 長時間の使用に耐えるよう、レジ画面で重いアニメーションや常時通信をしない |
| プライバシー | 購入者の情報は保持しない。データは端末の中に置き、同期を使う場合だけクラウドに置く |
| 可搬性 | 全データをCSVやJSONで書き出せる(サービスに閉じ込めない) |
| 配布への備え | サークル固有の値(サークル名、イベント種別の一覧、既定値など)をコードに書き込まず、設定として持つ。アクセス制御はサークル単位で行う |

## 10. 推奨する技術構成(案)

| 層 | 案 | 理由 |
|---|---|---|
| アプリ形態 | **PWA**(ホーム画面に追加して使う) | ストア審査が不要。iOSとAndroidの両方で動き、オフラインにも対応できる。配布するときもURLを渡すだけで済む |
| フロント | React + Vite + TypeScript | |
| 端末内の保存 | IndexedDB(Dexie.js) | オフライン前提の追記型ログに向く |
| 同期 | Supabase(Postgres + Auth + Realtime) | 複数端末の同期。売り子は匿名ログイン + 招待トークンで参加できる。行単位のアクセス制御(RLS)をサークルIDで掛け、売り子にはそのイベントの販売記録の追加だけを許可する。無料枠で足りる見込み |
| ホスティング | Vercel など静的ホスティング | |
| グラフ | Recharts など | |

MVPから同期を入れる。ただし、各端末は常に端末内のデータを正として動き、クラウドは端末どうしで記録を受け渡すための中継として使う。クラウドに一切つながらなくても、ファイルでの取り込み(F-1006)で記録を統合できる。

- 完売した頒布物について、完売時刻による補正を含めた刷り部数の提案が根拠つきで表示される
- 受託分を自分の分と同じ操作で記録でき、終了後に持ち主別の精算書が自動で出る。持ち主を付け替えると精算書が再計算される
- 2台の端末をどちらも機内モードにして、それぞれ150取引を記録する。通信を戻すと、両方の端末で合計300取引・同じ売上合計になり、重複も欠落もない
- 通信を戻さずに、ファイルでの取り込みだけで同じ結果になる
- 売り子の端末からは、価格やマスタを変更できない
- 預かり金額を入れるとお釣りが表示され、終了時の現金の理論残高と一致する
- 印刷費30,000円・頒布価格800円の頒布物で、損益分岐部数が38部と表示され、累計の販売部数との差(あと何部か)がグラフに出る
- イベントの経費を入力すると、そのイベントの損益分岐売上と、実績が黒字か赤字かがグラフに出る
- 通販で減った分を棚卸しで入力すると、在庫が実際の数に合い、需要予測には影響しない
