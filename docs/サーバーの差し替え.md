# サーバーの差し替え(Issue #45)

同期先をいまの Supabase から別のサービスに移すときの手引きです。2026-11-16 の時点では、移す準備だけを済ませています。Supabase は使い続けています。

## アプリとサーバーの境目

アプリは端末の中のデータベース(Dexie)を正として動きます。サーバーは、端末どうしの中継とバックアップに使っているだけです。

サーバーとのやり取りは、`src/server` に集めました。

| ファイル | 役目 |
|---|---|
| `src/server/types.ts` | アプリが使う形(`ServerBackend`・`AuthSession`) |
| `src/server/index.ts` | どのサーバーを使うかを選ぶ、ただ1つの場所(`VITE_SERVER`) |
| `src/server/supabase/` | Supabase での実装。Supabase のライブラリを読み込むのは、ここだけ |

`src/server/boundary.test.ts` が、`src/server/supabase` の外で Supabase を読み込んでいないかを確かめます。

`ServerBackend` に要るものは、次の3つです。

1. **同期**(`remote()` が返す `Remote`、`src/sync/engine.ts`)
   - `push(table, rows)`: マスタは `client_updated_at` の後勝ち、台帳は同じ主キーなら無視
   - `pull(table, since, limit)`: `server_seq` が `since` より大きい行を、小さい順に返す
   - `heads()`(なくてもよい): 表ごとの最新の `server_seq`
2. **ログインと招待**(`auth`、`src/auth/account.ts` の `AuthBackend`)
   - サークル主: メールのコード(またはリンク)と Google でログインする。新しいアカウントは作らせない(#25)
   - 売り子: 招待のリンクから、登録なしで(匿名で)参加する
   - 招待の作成・一覧・取り消しと、受け取り(`redeemInvite`)
3. **ログインの状態**(`getSession`・`onSessionChange`・`signOut`・`returnedFromLogin`)

## 新しいサーバーで守ること

いまは Supabase の中で、`db/schema.sql` が守っています。移す先でも、同じ決まりが要ります。

- **見える範囲と書ける範囲**
  - サークルの中だけを読み書きできる
  - 売り子は、参加しているイベントの分だけ見えて、販売と在庫の動きを追記できる
- **台帳は追記だけ**: 販売と在庫の動きは、書き直しも削除もできない。確定したイベントには、売り子は書けない
- **マスタは後勝ち**: `client_updated_at` が古い書き込みは無視する。書き込むたびに `server_seq` を振る
- **親子のサークルが同じ**: ほかのサークルの品目や場所を指す行は断る(`check_same_circle`)
- **サークルの作成**: `create_circle` が、作った人をサークル主として登録する
- **招待**: トークンはハッシュだけを保存し、期限と取り消しを確かめる(`redeem_invite`)

`db/schema.sql` が使う Supabase 専用のものは、`auth.uid()`・`auth.jwt()` の2つの関数と、`authenticated`・`anon` の2つの役割だけです。`db/test-schema.mjs` は、これらを自前で作って動かしています。そのため、移す先が Postgres なら、`db/schema.sql` と、その74項目のテストをほぼそのまま使えます。

## 新しいサーバーを足す手順

1. `src/server/<名前>/` を作り、`ServerBackend` を返す関数を書く
2. `src/server/index.ts` の `pick()` に、`VITE_SERVER=<名前>` のときの分かれ道を足す
3. 作った `Remote` で `describeRemoteContract`(`src/sync/remoteContract.ts`)を呼ぶテストを書き、通るか確かめる
4. 画面の言葉でサービスの名前が要るときは `server.name` を使う

## 移す日の手順

1. イベントのない時期を選ぶ
2. Supabase のバックアップ(`backup.yml`)を手で走らせ、新しいサーバーへ入れる
3. Vercel の環境変数に `VITE_SERVER` と新しいサーバーの接続先を入れて、公開し直す
4. 端末は、新しい版を読み込むと新しいサーバーに同期する。ただし、ログインはし直しになる。送信待ちの記録は端末に残り、ログインし直せば送られる
5. しばらくは Supabase を消さずに残す

## Supabase に合わせてあって、移すときに見直すもの

- `.github/workflows/keepalive.yml`: 一時停止を防ぐ毎日の書き込み。止まらないサービスに移したら要らない
- `.github/workflows/backup.yml`: `pg_dump` で書き出す。移す先が Postgres なら、接続文字列を差し替えるだけで使える
- `src/pages/LoginPage.tsx`
  - 続けて送れるまでの秒数(60秒)
  - コードの桁数の説明
- `docs/ログインのメール送信.md`: Supabase の送信設定の手順

## 移す先の案

詳しくは Issue #45 にあります。

| 案 | 中身 | `db/schema.sql` は |
|---|---|---|
| A | Cloudflare Workers + D1 | 使えない。SQLite なので、権限とトリガーを API の中で書き直す |
| B | Neon(Postgres)+ Workers の API | そのまま使える。API が `auth.uid()` に当たる値を入れてから SQL を流す |
| C | Firebase | 使えない。セキュリティルールで書き直す |
| D | サーバーなし | 要らない。ただし、同期と売り子の招待をやめる |
