# haifu-stock

同人誌即売会などのイベントで、頒布物の持ち込み数・売上・釣り銭・受託分をスマホで記録し、終了後に自動で集計して、次回の刷り部数の目安や損益分岐点を出すアプリです。

サークル主と売り子が別々のスマホで同じデータに記録でき、会場で電波がなくても動くことを前提にしています。

主な機能:

- **レジ**: タップでカートに入れて「決済」で記録。値引き、預かり金額とお釣り、キャッシュレスの支払い、取り置きの受け渡し、見本誌などの無償出庫、取り消し、画面のロック、休憩・離席
- **準備**: 持ち込む品目と数、イベント価格、レジの並び順、取り置き、釣り銭(目安の提案つき)、経費、前回のイベントからのコピー
- **終了処理**: 同期の確認 → 残数確認 → 現金の数え合わせ → 受託分の精算書 → 在庫への反映。確定のやり直しもできる
- **レポートと分析**: 時間帯ごとの売上、黒字になった時刻、持ち主別・端末別・支払い方法別の内訳、よく一緒に買われた組み合わせ、イベントの比較、刷り部数の目安(3案)、頒布物別・イベント別の損益分岐、刷り部数のシミュレーション、価格の試算。グラフは画像で保存できる
- **同期**: 売り子は QR コードで参加。オフラインで記録した分は、つながったときに送る。ファイルでの受け渡しもできる
- **データ**: バックアップの書き出し・読み込み、CSV(販売・在庫の動き・イベント)

## 動かす

Node.js 20 以上が必要です。

```bash
npm install
```

```bash
npm run dev
```

ブラウザで http://localhost:5173 を開き、サークル名を入れて始めます。ホームの「品目」で頒布物と刷り記録を登録し、「イベントを作る」で持ち込み数・釣り銭・経費を準備すると、レジで記録できます。

同期先(Supabase)を使う場合は、次の「Supabase の準備」を済ませてから `.env.example` を `.env` にコピーし、接続先を入れます。設定しなければ、ログインと同期は使えず、端末の中だけで動きます。

## Supabase の準備

1. プロジェクトを作り、SQL エディタで `db/schema.sql` を実行する(表・権限・トリガー・集計ビュー・同期用の関数 `sync_heads()` まで入る)。すでに動いているプロジェクトに変更を足すときは、`schema.sql` との差分をマイグレーションとして入れる。**新しい列や表を使う版を公開するときは、先にマイグレーションを入れてから公開する**(古い表を消すときは逆に、すべての端末が新しい版になってから消す)
2. Authentication → Sign In / Providers で、**Email** と **Anonymous sign-ins** を有効にする(匿名ログインは売り子の参加に使う)
3. (任意)独自のメール送信(SMTP)を設定した場合は、Authentication → Emails の **Confirm signup** と **Magic Link** のテンプレートに6桁のコード `{{ .Token }}` を入れると、コードでもログインできる。標準のメール送信ではテンプレートを編集できないので、メールのリンクでログインする
4. Authentication → URL Configuration の Site URL に、アプリを置くURLを入れる。Redirect URLs に `<アプリのURL>/login`(開発中は `http://localhost:5173/login` も)を入れる
5. (任意)Google でのログイン: Google Cloud で OAuth クライアント(ウェブアプリ)を作り、承認済みのリダイレクト URI に `https://<プロジェクト>.supabase.co/auth/v1/callback` を入れる。クライアントIDとシークレットを Authentication → Sign In / Providers → Google に入れて有効にすると、ログイン画面に「Google でログイン」が出る

### ログインと参加のしかた

- **サークル主**: ホームの「ログイン」から、Google のアカウントか、メールのリンクでログインする。ログイン前にこの端末で記録したデータは、そのままサーバーに送られる。メールでのログインは登録済みのアカウントだけ(新しいアカウントは作らない)。新しいサークルを作れるのは、すでにサークル主のアカウントだけ(最初の1つを除く。Issue #25)
- **売り子**: サークル主がホームの「売り子を招待」で出すQRコードを読み、「参加する」を押す。登録は不要で、参加したあとは電波がなくても記録できる

### 一時停止を防ぐ・バックアップ(GitHub Actions)

- **一時停止を防ぐ**([keepalive.yml](.github/workflows/keepalive.yml)): Supabase の無料プランは、7日ほど使われないとプロジェクトを一時停止する。2日おきにデータベースへ軽い問い合わせをして、止まらないようにする。止まっていたらジョブが失敗し、GitHub から通知が届く(管理画面の **Resume project** で再開できる。止まってから90日を過ぎると再開できない)。止まっている間にアプリで同期すると「同期先が一時停止しています」と出る。記録は端末に残り、再開すれば送られる
- **バックアップ**([backup.yml](.github/workflows/backup.yml)): 毎週月曜、データベース(アプリの表と、ログインのアカウント)を書き出し、暗号化して Actions の成果物に置く(90日残る)。リポジトリの Settings → Secrets and variables → Actions に、次の2つを置くと動く
  - `SUPABASE_DB_URL`: Supabase の管理画面の **Connect** →「Session pooler」の接続文字列(`[YOUR-PASSWORD]` をデータベースのパスワードに置き換える)
  - `BACKUP_PASSPHRASE`: 暗号化の合言葉。自分で決めて、パスワード管理ソフトなどに控える(**なくすと戻せない**)
- GitHub は、リポジトリが60日動きのないとき、定期実行を止める(止める前にメールが届く)。届いたら Actions の画面で有効にし直す

### バックアップから戻す

1. GitHub の Actions → Backup database → 戻したい日の実行 → Artifacts から取り出し、zip を解く
2. 復号して開く: `gpg -d haifu-backup-YYYYMMDD.tar.gz.gpg > backup.tar.gz` → `tar -xzf backup.tar.gz`(`haifu.dump`・`auth.dump` が出る)
3. 中身を確かめるだけなら: `pg_restore --list haifu.dump`
4. 新しい Supabase プロジェクトに戻すとき(PostgreSQL 17 の `pg_restore` を使う。接続先は Session pooler):
   - `pg_restore --no-owner --no-privileges --data-only -d "<接続文字列>" auth.dump`(ログインのアカウント)
   - `pg_restore --no-owner --no-privileges -d "<接続文字列>" haifu.dump`(表・関数・RLS・データ)
   - 権限は書き出しに入れていないので、`db/schema.sql` の中の `grant` / `revoke` の行を SQL エディタで流し直す
   - アプリの `.env` の接続先を新しいプロジェクトに変えて公開する

## 確認する

| コマンド | 内容 |
|---|---|
| `npm test` | 記録・集計・同期・終了処理・招待のテスト(端末2台のオフライン記録、ファイルでの取り込み、確定時の反映など) |
| `npm run test:db` | `db/schema.sql` の検証(権限、追記専用の台帳、集計ビューなど) |
| `npm run typecheck` | 型チェック |
| `npm run build` | 本番用のビルド(PWA) |

GitHub に push すると、GitHub Actions([.github/workflows/ci.yml](.github/workflows/ci.yml))が型チェック・`npm test`・`npm run test:db`・ビルド・`npm audit` を走らせる。失敗すると GitHub から通知が届く。依存ライブラリの更新は Dependabot が毎週 pull request で知らせる。

ビルドした版を、本番と同じヘッダーで確かめるときは `dist` を静的に配る(Service Worker と新しい版の知らせは、開発用のサーバーでは動かない)。設定の下に、動いている版(コミットの番号)が出る。

## 構成

```
src/
  db/          端末内のデータベース(IndexedDB / Dexie)。列名は db/schema.sql と同じ
  domain/      記録(販売・無償出庫・取り消し・在庫移動)と集計。画面に依存しない
  sync/        同期(送信待ち → サーバー、サーバー → 端末)とファイルでの取り込み
  app/         データベースと同期を画面につなぐ部分
  auth/        ログインと売り子の招待
  pages/       画面(最初の設定、ホーム、品目、棚卸し、イベントの準備、レジ、履歴、終了処理、レポート、分析、設定、ログイン、招待、参加)
  pages/register/  レジの部品(カート、長押しのメニュー、取り置き、決済の表示、画面のロック)
  components/  画面の部品
db/            Supabase 用のスキーマと検証
docs/          要件定義書
prototype/     レジと終了処理の試作品(1ファイルで動く)
```

### しくみの要点

- 端末のデータベースを常に正として動き、サーバーは端末どうしで記録を受け渡す中継として使う
- 販売・取り消し・在庫移動は追記だけ。主キーは端末で発行する UUID v7 なので、2台がオフラインで記録しても衝突しない
- 記録はすべて送信待ち(`outbox`)に積み、通信できるときに親テーブルから順に送る。1つの表が送れなくても、ほかの表は続ける(親の表が送れないときは子の表は待つ)
- 受け取るときは、`sync_heads()` で表ごとの最新の番号を1回で調べ、変わった表だけを `server_seq` の続きから取る。同期の間隔は、変化がなければ最長2分まで延ばし、記録したらすぐ送る
- 残数・売上・完売時刻は保存せず、台帳から計算する(`src/domain/ledger.ts`)
